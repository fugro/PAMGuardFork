# Releasing a new pinned PAMGuard jar

This fork (`fugro/PAMGuardFork`) publishes a versioned, runnable fat jar as a **GitHub Release
asset**. A GitHub Actions workflow does the build automatically — you just push a tag.

## TL;DR

```bash
git switch fugro                     # do your work on the fugro branch
# ... commit your changes ...
git push origin fugro

git tag fugro-v2.02.19-1             # <upstream-version>-<iteration>, bump each release
git push origin fugro-v2.02.19-1     # <-- this push triggers the build
```

Then watch the **Actions** tab. When the run finishes, the jar is attached to the release.

## How it works

- The workflow lives at `.github/workflows/release-jar.yml`.
- It triggers on pushing any tag matching **`fugro-v*`** (`on: push: tags: ['fugro-v*']`).
- It checks out the tagged commit, sets up **Temurin Java 21**, runs
  `mvn -B clean install shade:shade -DskipTests`, and attaches `target/Pamguard-*.jar` to a
  GitHub Release via `softprops/action-gh-release`.
- **Java 21 is required** — the code uses Java 21 APIs (e.g. `ArrayList.getLast()`) and the pom's
  active profile compiles with `<release>21</release>`. Building on Java 17 fails to compile.

## Step by step

### 1. Make and commit your changes
Work on the `fugro` branch (keeps patches off `main`):
```bash
git switch fugro
# edit code...
git add <changed files> && git commit -m "Describe the change"   # not `git add -A`, see note below
git push origin fugro
```

### 2. Choose a version tag
Format: **`fugro-v<upstream-version>-<iteration>`**, e.g. `fugro-v2.02.19-1`.
Bump the trailing iteration for each new build of the same upstream version; change the
upstream-version part when you rebase onto a new upstream release. `git tag -l 'fugro-v*'`
lists the tags already used.

> Tags are immutable triggers: pushing a **new** tag starts a build. Pushing a tag name that
> already exists does **not** re-trigger. To rebuild the same tag, delete it first:
> ```bash
> git push origin :refs/tags/<tag>   # delete remote
> git tag -d <tag>                    # delete local
> git tag <tag> && git push origin <tag>
> ```

### 3. Tag and push (this starts the build)
```bash
git tag fugro-v2.02.19-1
git push origin fugro-v2.02.19-1
```

### 4. Watch the build
- GitHub web: repo → **Actions** tab → the `release-jar` run.
- CLI: `gh run list -R fugro/PAMGuardFork` / `gh run watch -R fugro/PAMGuardFork`.

A run takes a few minutes (the compile alone is large). If it fails on compilation, the most
common cause is a Java version mismatch — confirm the workflow is on Java 21.

## Final location of the jar

When the build succeeds, the fat jar is attached to the release for that tag. The stable,
tokenless (public repo) download URL is:

```
https://github.com/fugro/PAMGuardFork/releases/download/<tag>/Pamguard-<version>.jar
```

Example:
```
https://github.com/fugro/PAMGuardFork/releases/download/fugro-v2.02.19-1/Pamguard-2.02.19.jar
```

This is the immutable URL a Docker image's `ADD` consumes at build time. Confirm the exact
asset filename on the **Releases** page (or `gh release view <tag> -R fugro/PAMGuardFork`) and
make sure the Dockerfile's version/jar-name build args match.

Browse releases:
- Web: repo → **Releases** (`/releases`); `/releases/latest` redirects to the newest.
- CLI: `gh release list -R fugro/PAMGuardFork`, `gh release view <tag> -R fugro/PAMGuardFork`,
  `gh release download <tag> -p '*.jar' -R fugro/PAMGuardFork`.

## Notes

- For tag pushes GitHub runs the workflow file **in the tagged commit**, so it must be on `fugro`.
  It is also kept on `main` so the fork's default branch shows how releases are built.
- Don't use GitHub's **"Sync fork"** button: it resets/merges `main` to upstream `main` (which may
  be mid-development and not compile). Update `main` and `fugro` onto upstream release tags instead.
- `dependency-reduced-pom.xml` is regenerated by the shade plugin on every build, so it shows as
  modified afterwards. It is tracked upstream — never commit it in fork patches; reset it with
  `git restore dependency-reduced-pom.xml`.
- The published jar targets **Java 21**, so the Docker runtime base image must be
  `eclipse-temurin:21-jdk` (a Java 21 jar won't run on a 17 JRE).

## Updating to a new upstream release

The fork is "an upstream release plus our patches on top". Updating means moving our patches onto
a newer upstream release (a **rebase**). Patches that upstream has merged meanwhile (e.g. our PRs)
are recognised and dropped automatically.

**Always update onto an upstream release tag (`V<version>`), never onto `upstream/main`.**
`upstream/main` is work in progress and may not compile (after V2.02.19 it didn't for weeks).
Get notified of releases on github.com/PAMGuard/PAMGuard → **Watch → Custom → Releases**.
Don't use GitHub's **"Sync fork"** button (see Notes).

Below, `<new>` is the new upstream version (e.g. `2.03.00`, tag `V2.03.00`) and `<old>` the one
the fork is on now.

### 1. Fetch and inspect

```bash
git fetch upstream --tags && git fetch origin
git tag -l 'V*' --sort=-v:refname | head -3      # latest upstream release tags
git status --short                               # no modified tracked files (untracked is fine)

git cherry -v V<new> fugro                       # + = still carried, - = already upstream (dropped)
```

Local and remote branches must match before you rewrite them:

```bash
git rev-parse fugro origin/fugro                 # both lines must be identical
git rev-parse main  origin/main
```

If a remote branch differs, look at what is there before continuing (`git log --oneline
main..origin/main`) — someone may have pushed, or pressed "Sync fork" on GitHub. Note the remote
commits; they are used in step 7 so a push can't overwrite anything you haven't seen:

```bash
OLD_FUGRO=$(git rev-parse origin/fugro)
OLD_MAIN=$(git rev-parse origin/main)
```

### 2. Make backups

```bash
git branch backup/fugro-<old> fugro
git branch backup/main-<old>  main
```

These are local bookmarks; everything can be reset to them (see "Undo" below).

### 3. Optional: trial run in a throwaway worktree

Recommended for bigger upstream releases. A worktree is a second checkout, so the real branches
stay untouched:

```bash
git worktree add --detach /tmp/pamguard-trial fugro
cd /tmp/pamguard-trial
git rebase V<new>                                # conflicts? you now know what to expect
mvn -B clean install shade:shade -DskipTests
cd - && git worktree remove --force /tmp/pamguard-trial
```

If the build fails, check whether plain `V<new>` builds on its own
(`git switch --detach V<new>` in the worktree) before blaming our patches.

### 4. Rebase `fugro`

```bash
git switch fugro
git rebase V<new>
```

On a conflict: edit the file(s), `git add <file>`, `git rebase --continue`.
To cancel and return to the state before the rebase: `git rebase --abort`.

### 5. Build and check

```bash
mvn -B clean install shade:shade -DskipTests     # -> target/Pamguard-<new>.jar
git restore dependency-reduced-pom.xml           # regenerated by the build, never commit it
git log --oneline V<new>..fugro                  # only our patches should be listed
```

### 6. Rebuild `main`

`main` only carries the release workflow on top of the release. Rebuild it from the tag and the
workflow commits on `fugro` rather than rebasing it (keep workflow commits workflow-only, so this
stays clean):

```bash
git switch main
git reset --hard V<new>
git cherry-pick $(git rev-list --reverse V<new>..fugro -- .github/workflows/)
git diff --stat main fugro                       # should show only our code patches
git switch fugro
```

### 7. Push

A rebase rewrites history, so a force push is needed. `--force-with-lease=<branch>:<commit>`
only succeeds if the remote is still at the commit noted in step 1:

```bash
git push --force-with-lease=fugro:$OLD_FUGRO origin fugro
git push --force-with-lease=main:$OLD_MAIN   origin main
```

Existing `fugro-v*` tags keep pointing at the old commits, so already released jars (and Docker
images using them) are unaffected.

### 8. Release and roll out

- Tag `fugro-v<new>-1` on `fugro` and push the tag (see "Step by step" above). Watch the build.
- Update the jar URL in the Docker image. The jar name follows the pom version
  (e.g. `Pamguard-2.02.19.jar`); check it on the release page.
- Once the new version is in use, delete the backups: `git branch -D backup/fugro-<old> backup/main-<old>`.
- Delete `fix/*` branches whose PRs upstream has merged (local and on `origin`).

### Undo

Until the backups are deleted, a branch can be put back exactly as it was:

```bash
git switch fugro
git reset --hard backup/fugro-<old>
git push --force-with-lease origin fugro         # only if the rebased branch was already pushed
```

(Same for `main` with `backup/main-<old>`.)
